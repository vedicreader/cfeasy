cloudflare

The CF class: Cloudflare DNS records and tunnels through the official Python SDK

CF

CF holds one connection to the Cloudflare API and offers a method for each job. The token comes from the token argument, or from the CLOUDFLARE_API_TOKEN environment variable when you leave it out. timeout is the number of seconds to wait for each request, and any other keyword arguments go straight to the SDK’s Cloudflare client.

Every method returns plain dictionaries and lists, converted from the SDK’s objects, so the results print and serialise without extra work.

The methods come in three groups:

  • Zones and DNS records: zones, zone_id, dns_records, create_record, delete_record and upsert_record. A zone is a domain you manage on Cloudflare. The low-level methods take a zone ID; upsert_record takes the domain name and looks the ID up itself, so it is the one to use in most code.
  • Tunnels: account_id, tunnels, tunnel_id, create_tunnel, delete_tunnel, tunnel_token and tunnel_cname. Tunnels belong to an account rather than a zone, so tunnels, tunnel_id, create_tunnel, delete_tunnel and tunnel_token take an optional account_id and use your first account when you leave it out. tunnel_cname writes the DNS record that points a name at a tunnel.
  • Shortcuts: verify checks the token without changing anything, and setup_tunnel creates a tunnel, its DNS record and its token in one call.

upsert_record keeps one record per name. It walks the records that already have the name. The first one with the same type and content is kept and returned, and any record it passed on the way is deleted. If none match, every record under the name is deleted, whatever its type, and the new record is created. A name without a dot is treated as a subdomain of the domain.

Least-privilege token setup

Give the token only the permissions cfeasy needs. Create a custom token in the Cloudflare dashboard under My Profile -> API Tokens -> Create Token:

What it is for Permission
DNS records Zone -> DNS -> Edit (limit it to your zone)
Finding the account ID for tunnel calls Account -> Account Settings -> Read
Creating, listing and deleting tunnels Account -> Cloudflare Tunnel -> Edit

verify confirms the token works before you change anything. It checks that the token is active, that it can see an account, its zones (or the one zone named by domain) and that account’s tunnels. It returns ok, the token status, the account ID, the zone names, the tunnel count and an errors dict naming each check that failed. Account-owned tokens are checked against the account endpoint. The examples below ran against a real account and are not run by the docs build. The second setup_tunnel call serves the domain sankalpa.sh itself instead of a subdomain.

Cache rules and purges

A zone keeps its cache rules and its custom firewall rules in rulesets, one entrypoint ruleset per phase. ruleset_upsert puts your rules into the entrypoint for phase and keeps every rule there that it does not own, with all its keys, such as logging or ratelimit; only Cloudflare’s read-only version, last_updated and categories are left out of the update. A rule is matched by its ref, so give each rule a stable ref. When the rules with those refs already match yours on the usual keys and every key your rules set, it sends nothing and returns False; otherwise it writes the merged list and returns True. Running it on every deploy is safe. The token needs Zone -> Cache Rules -> Edit for the cache phase, and Zone -> Zone WAF -> Edit for http_request_firewall_custom.

purge empties the zone’s cache by URL files, by URL prefixes, or everything. Files and prefixes go in separate requests, files first, because the API takes one kind per request. A rate limit (HTTP 429 or Cloudflare’s code 1134) or a timeout is retried up to tries times in all, waiting wait seconds and doubling the wait each time. Some plans or tokens refuse a prefix purge, with HTTP 403 or a 400 that names the plan or a permission. With fallback_all=True, the default, such a refusal becomes a purge of everything. Any other error, including a rate limit that outlasts the retries, raises and purges nothing more. The return value lists the purge requests that succeeded: after a fallback, the files purge when it ran first, then the purge of everything, so a caller can tell when the fallback ran.

def fake_rules(rules=()):
    c, calls = CF('x'), []
    R = lambda d: NS(model_dump=lambda exclude_none=True: d)

import httpx
from unittest import mock
from cloudflare import APITimeoutError, BadRequestError, PermissionDeniedError, RateLimitError
_rq = httpx.Request('POST', 'https://api.cloudflare.com/client/v4/zones/z/purge_cache')
def cf_err(cls, status, code, msg): return cls(msg, response=httpx.Response(status, request=_rq), body=dict(errors=[dict(code=code, message=msg)]))
refused = lambda: cf_err(PermissionDeniedError, 403, 10000, 'not on this plan')
def fake_purge(fails=None):
    'A client whose purge raises, for each kind of purge in `fails`, the errors listed there in turn, then succeeds; `calls` records each request.'
    c, calls, fails = CF('x'), [], {k: list(v) for k, v in (fails or {}).items()}
    def purge(zone_id, **kw):
        calls.append(kw)
        if (q := fails.get(first(kw))) and (e := q.pop(0)()): raise e
    c._c = NS(cache=NS(purge=purge))
    return c, calls

Helpers

repo_root returns the top folder of the git repository you are working in, found by walking up from the current directory until it finds a .git entry. It returns None outside a repository.

cfeasy ships a SKILL.md file that tells coding agents such as Claude Code how to use the library. mv_skill_md copies it into a project’s .agents/skills/cfeasy/ and .claude/skills/cfeasy/ folders, where those agents look for skills. By default it only prints where it would copy the file; pass dry_run=False to copy it. The project root is dir if you give one, otherwise the repository root, otherwise the current directory.
